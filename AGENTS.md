# Project guidance

The canonical repository for this project is https://github.com/fayazamir1991/sms. Continue development against this repository. Read the current branch and remote state before making changes; preserve unrelated user changes. Do not force-push.

This is Delneveshte, a native Java Android app for personally approved romantic SMS from the user's own SIM. The original test handset is Xiaomi Android 14 with two SIMs, but the product supports Android phones across manufacturers. Use standard Android settings intents with fallbacks; no manufacturer-specific setup requirements. The UI is Persian and RTL. Google Messages should remain the default SMS application.

Preserve these requirements:

- The user configures recipient, sending SIM, daily message count and allowed time window.
- Offer several texts for selection/editing. Only exact approved recipient/body/SIM snapshots can be sent. Settings changes must never redirect previously approved messages.
- Tapping «افزودن به صف» is the user's approval: add directly with a toast, no extra dialog or navigation. Editing shows three explicit sending choices: immediate, random and fixed date/time. Immediate sending always requires a confirmation; cancellation must create no queued or history entry.
- Empty queue means no send. Pausing cancels scheduling. No automatic retries after an ambiguous sending result.
- Recheck the allowed window at actual scheduled execution. Restoring alarms after reboot or reopening must never send a message directly.
- Do not send real SMS from development tools. Handset testing requires the user's explicit confirmation in the app.
- Never commit local credentials, signing keystores, personal recipient settings or build caches.

Primary backend deployment is Docker on Hamravesh: Node 24, persistent SQLite under /data, one replica. Cloudflare Workers + D1 is optional and manual only. Proposals come from the server catalog, cached locally; retain the offline fallback. Queue changes and durable sync events must be atomic. Server acknowledgements must never discard newer local revisions. Preserve nondestructive DB v1/v2→v3 migration, including existing approved schedules and sync identities. Cloud synchronization is enabled by default without a confirmation dialog, as explicitly requested by the product owner. Synchronization is always managed by the app and the build-time HTTPS endpoint. No user-facing sync box, disable control or server editor. Ignore legacy disabled flags/custom URLs while preserving installation credentials, approved snapshots and outbox data. Never enable a paid hosting plan. Do not claim unlimited AI generation or actual handset/Google Messages verification without evidence.

The user requires each version to have a GitHub Release with an APK asset. Increment versionCode/versionName in app/build.gradle, add Persian notes under docs/releases/vVERSION.md, and let the successful main-branch workflow publish the version. Existing release tags/assets must not be silently overwritten. Releases remain experimental. Preserve the original chat-installed signing identity pinned in signing-certificate.sha256. Never generate a replacement signing key; refuse release publication on a mismatch. Never overwrite existing release assets.

Build with JDK 17/21, Android SDK platform 35 and build-tools 35.0.0, Gradle 8.9 and Android Gradle Plugin 8.7.3. See docs/BUILD.md. Run the relevant compile, lint and CoreChecks validation when changing behavior. No unnecessary Android dependencies.

Catalog imports must retain attribution, deduplicate excerpt text and preserve admin edits/deactivations. Full Ganjoor processing is one-time; nightly collection runs at 02:00 Asia/Tehran, cap 20/day by default. See docs/CATALOG-IMPORT.md.

Version 0.7 requirements: Namnak is excluded. Ganjoor uses balanced-v3 multi-signal personal/emotional selection plus reviewed exceptions; do not regress to a love-word match or the 24-item-only restriction. Keep policy rules, sample report and stored selection metadata auditable. Migration 0008 is the owner-authorized one-time FULL server data reset; do not repeat it on future deployments. Browse/search pages hold 20 messages and append via a signed stable cursor; SMS approval snapshots remain immutable. Source details belong only in the card overflow menu.

Version 0.9: search is a dedicated bottom-navigation tab across all categories. Typing filters immediately and debounces remote requests by 350 ms; clear empties results (as superseded by the 0.17 requirement). Search combines matching cached/bundled messages with all server matches and appends 20 at a time without duplicates. Production SQLite must detect result-bearing statements using prepared-statement columns, including WITH/CTEs; test the real SQLiteStore and Docker, not only the test adapter. Home has no recipient/SIM instructions. Cards show only text and two compact random/fixed actions; tap/long press opens all actions and source details.

Fixed-time messages persist sendMode=FIXED and requestedAt, independent of random daily count/window. Global pause still stops automatic sending and retains requestedAt. Missed paused fixed messages fail instead of being randomized; scheduled alarms may execute up to 30 minutes late for OS delays. Reconcile and reboot only arm alarms, never send directly. Immediate intents use IMMEDIATE status and never enter the automatic queue. Never change approved body/recipient/SIM during planning or upgrade.

Design direction: modern messenger components inspired by the open TelegramUI library and the 2026 Telegram Android navigation, adapted to native Java and Persian RTL. The owner explicitly rejected the classic 7.8 blue appearance. The owner replaced the old lacquer palette and explicitly selected the latest comparison's palette 2, light violet and primrose: brand #8172B5, complement #F4E89C, background #FBF9FD. Use #62528E for small colored text and #7564A8 for white-labeled filled controls (contrast above 4.5:1). Keep surfaces flat and pastel; no old lacquer glints, red/gold branding or gradients. Semantic errors/success retain their meaning. Sources, tokens and the distinction between the inaccessible original Figma layers and the inspected open component sources are documented in docs/DESIGN-SYSTEM.md. Bundle Vazirmatn with OFL notices. Preserve two card actions, global live search, all three sending modes, the signing identity and the existing SQLite schema.

Navigation and action icons now use Font Awesome Free 7.3.1 Classic Solid, adapted from the original SVG paths into VectorDrawable. Preserve CC BY 4.0 attribution, original source manifest and bundled license; the settings credits dialog exposes licensing to users. No paid icon pack or icon-font runtime dependency is needed.

Version 0.12: every random approval must atomically persist a concrete future plannedAt/planDay, including while paused/offline. Reserve across future days within the daily random quota, counting existing random reservations and submitted attempts. Preserve valid future slots when adding messages, pausing or reconciling; repair missing/expired/out-of-window/over-quota random slots without sending. Queue sorts by time and exposes a date/time editor that changes the same pending record to FIXED with a revision/status guard, serialized with alarm sending. Keep approved body/recipient/SIM/sync identity immutable; edits create durable sync revisions. Never edit a claimed, sent, cancelled or stale record. No schema reset.

Queue cards support tap, long press and mouse context click to open a Font Awesome action menu: edit time, immediate send, remove and copy. Preserve immediate-send/removal confirmations; opening or dismissing the menu must not mutate or send.

Version 0.14: settings have no nickname field, sync section or server editor. New suggestions use the neutral default name; historical approval snapshots are unchanged. All Font Awesome paths retain their source proportions, centered on square vector viewports. Image buttons use CENTER_INSIDE with square touch targets of at least 48dp; do not stretch rectangular source SVG viewports into squares. General battery/background help uses standard Android intents and fallbacks, never MIUI/HyperOS component names.

Version 0.15: display queue/history/toast timestamps relative to local calendar days (today/tomorrow/day-after, not elapsed 24-hour intervals). Manual scheduling offers Today, Tomorrow, Other Date. Other Date uses a Persian/Solar Hijri calendar with Persian month/year navigation and Saturday-first weeks, backed by Android ICU (no Gregorian DatePicker). Preserve selected clock when changing day, guard past instants and cancel without mutations. Stored epoch values and all snapshot/revision guards remain unchanged. Queue cards show body, relative time and one 48dp Font Awesome trash action only; edit time, immediate send, copy and immutable recipient/SIM information live in the card context menu. Removal still confirms.

Version 0.16: use the compact UI metrics in UiMetrics.java. Separate visuals from input: 18/20dp icon canvas, 32dp card-icon surfaces, 40dp text-button surfaces with 4dp vertical insets, 48dp non-overlapping touch targets. Toolbar controls are quiet, search clear lives inside the field. Bottom navigation is docked below content, never an overlay; highlight only the icon badge. Settings secondary actions are lightweight rows. Preserve system font scaling and wrapping; never shrink accessibility touch targets or freeze text-button heights to achieve visual density. Sources and product-specific choices are documented in docs/UI-AUDIT-v0.16.md.

Inset/ripple visual backgrounds must report no layout padding. View.setBackground can otherwise overwrite explicit content padding, crowd chip labels, clip compound icons or inflate the search field. Keep visual insets independent of layout padding; preserve regression checks for chip spacing and the search container.

Version 0.17: bank/search have no message-count row. Search opens empty from either entry point; a blank or whitespace-only query must not show cached/fallback rows, loading/not-found text, pagination or issue a browse request. Clear cancels debounce, invalidates pending replies and empties results immediately. New entry resets the search; reselecting the active search tab refocuses it. Request editor focus and the soft keyboard after attachment/window focus; hide it when leaving search. Search result updates never rebuild the input or disrupt typing. Keep live 350ms global matching, caching and append pagination for nonempty queries. Test actual APK focus/IME and visible cards instead of relying on the removed counter.

Version 0.18: prose rows store body_formal and body_colloquial together. Default tone is colloquial; bank and global search use only the selected variant, with stale-response/cursor guards when tone changes. Poetry always uses its original body and never undergoes tone conversion. Preserve queue snapshots and outbox during additive schema 4 cache migration. Backfill legacy prose and seed 2000 finite original paired compositions idempotently; preserve admin pair edits/deactivations. No catalog reset. Document the compositional method transparently in docs/CATALOG-TONES.md. Keep source/reading metadata outside SMS bodies.

Version 0.19: use an inline native tone switch with immediate persistence, no picker dialog. Bank-only pull-to-refresh starts a new first-page request, preserves tone/category, invalidates stale replies, ends on success/failure and leaves search/pagination semantics unchanged. Compose stays on the physical RIGHT in RTL. Fresh installs default to enabled automatic scheduling but readiness and approved-snapshot guards remain mandatory; missing permissions/settings must not turn the preference off. Preserve explicit pauses and legacy installs on upgrade. Never send from permission callbacks or reconciliation; only arm valid approved schedules.
