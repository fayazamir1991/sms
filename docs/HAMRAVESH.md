# راه‌اندازی روی هم‌روش با اتصال گیت‌هاب

مسیر اصلی استقرار اکنون Docker است؛ Cloudflare یا D1 و Secretهای آن‌ها لازم نیست. سرور و پنل مدیریت در یک کانتینر اجرا می‌شوند. API گوشی تغییر نکرده است. دیتابیس SQLite روی دیسک دائمی `/data` قرار می‌گیرد؛ هیچ دیتابیس جدا یا Redis لازم نیست.

## تنظیمات ساخت و اجرا

در دارکوب، یک اپ از منبع گیت بسازید و ریپوی `https://github.com/fayazamir1991/sms` را وصل کنید:

| تنظیم | مقدار |
| --- | --- |
| شاخه | `main` |
| Build context | `.`، ریشهٔ ریپو |
| Dockerfile | `Dockerfile` در ریشهٔ ریپو |
| پورت برنامه | `8080`، نوع HTTP |
| فرمان اجرا | پیش‌فرض Dockerfile؛ خالی بگذارید |
| تعداد نمونه / Replica | **۱** |
| دیسک دائمی | اتصال در مسیر **`/data`** با دسترسی نوشتن |
| Health check | `GET /healthz` روی پورت `8080` |
| مهلت شروع | حداقل ۳۰ ثانیه |
| توقف نرم | حداقل ۲۰ ثانیه |
| دامنه | دامنهٔ خود اپ با **HTTPS** فعال |

از روش استقرار با توقف نمونهٔ قبلی پیش از شروع نمونهٔ جدید، یا Recreate در صورت ارائهٔ این گزینه، استفاده کنید. SQLite و دیسک این نسخه برای یک نمونه طراحی شده‌اند؛ دو Replica یا دیسک اشتراکی شبکه‌ای برای چند نمونه مناسب نیست. دیسک باید قفل فایل استاندارد SQLite را پشتیبانی کند. افزایش تعداد نمونه به مهاجرت دیتابیس به PostgreSQL نیاز دارد.

حجم اولیهٔ پیام‌ها کم است؛ برای شروع یک دیسک کوچک کافی است. ظرفیت، منابع و هزینه را در حساب خودتان انتخاب کنید. کد هیچ سرویس یا پلن پولی نمی‌خرد. زمان و نام دقیق گزینه‌های کنسول ممکن است تغییر کند؛ [مستندات رسمی دارکوب](https://docs.hamravesh.com/darkube/) مرجع پنل است.

## متغیرهای محیطی خصوصی

این‌ها **متغیر زمان اجرای اپ در هم‌روش** هستند، نه Build Arg و نه فایل عمومی ریپو:

| نام | مقدار |
| --- | --- |
| `PUBLIC_URL` | آدرس واقعی عمومی اپ، مثل `https://YOUR-APP-DOMAIN`؛ بدون `/admin` یا مسیر اضافی |
| `SERVER_RUNTIME_SECRETS` | تمام JSON فایل خصوصی قبلی `SERVER_RUNTIME_SECRETS.json`، ترجیحاً در یک خط |

اگر واردکردن JSON در پنل سخت است، به‌جای `SERVER_RUNTIME_SECRETS` سه فیلد همان فایل را جدا ذخیره کنید:

- `DATA_ENCRYPTION_KEY`
- `SESSION_SIGNING_KEY`
- `ADMIN_TOKEN_SHA256`

`PORT=8080` و `DATA_DIR=/data` از قبل در Dockerfile تنظیم شده‌اند. رمز ورود مدیر همان فایل خصوصی **`ADMIN_LOGIN.txt`** است؛ مقدار `ADMIN_TOKEN_SHA256` هش آن رمز است و خودش رمز ورود نیست. Secretهای امضای اندروید فقط در GitHub می‌مانند و وارد کانتینر نمی‌شوند. هیچ رمز پیش‌فرض یا تولید کلید تازه در شروع کانتینر وجود ندارد؛ متغیر ناقص باعث توقف روشنِ راه‌اندازی می‌شود.

همان بستهٔ خصوصی قبلی را نگه دارید؛ این تغییر میزبانی نیاز به ساخت دوبارهٔ کلیدها ندارد. اگر قبلاً داده‌ای در Cloudflare ذخیره شده باشد، تغییر میزبان به‌تنهایی آن دیتابیس را منتقل نمی‌کند. مسیر Docker برای دیتابیس تازه آماده است؛ برای انتقال دادهٔ موجود باید خروجی و واردکردن آن جدا انجام شود.

## اولین راه‌اندازی و آپدیت‌ها

هنگام شروع، پیش از بازشدن پورت، مهاجرت‌ها در تراکنش اجرا می‌شوند. فقط در اولین راه‌اندازی دیتابیس، ۱۰۰۹ پیام یکتا شامل ۱۰۰۲ متن تألیفی و ۷ بیت وارد می‌شوند. سابقهٔ اجرای مهاجرت روی همان دیسک ذخیره می‌شود؛ ری‌استارت یا دیپلوی بعدی پیام تکراری نمی‌سازد و ویرایش مدیر را برنمی‌گرداند.

پس از Ready شدن:

1. `https://YOUR-APP-DOMAIN/healthz` باید پاسخ `ok: true` بدهد.
2. `https://YOUR-APP-DOMAIN/admin` را باز کنید و با رمز `ADMIN_LOGIN.txt` وارد شوید.
3. شمارندهٔ بانک اولیه باید ۱۰۰۹ باشد.

اگر ورود پنل خطای «مبدأ درخواست مجاز نیست» داد، `PUBLIC_URL` را دقیقاً برابر دامنه‌ای کنید که در مرورگر باز می‌کنید. HTTPS برای کوکی ورود پنل و اتصال اندروید لازم است؛ TLS در ورودی هم‌روش خاتمه می‌یابد و پورت داخلی کانتینر HTTP است.

## اتصال اپ اندروید و انتشار APK

دو راه وجود دارد:

- برای آزمایش، در تنظیمات اپ، «بانک پیام‌ها و همگام‌سازی» → «راه‌اندازی همگام‌سازی»، آدرس HTTPS سرور را وارد کنید و فعال کنید.
- برای اینکه APK از ابتدا آدرس درست داشته باشد، در GitHub → Settings → Secrets and variables → Actions → **Variables**، متغیر `API_BASE_URL` را برابر همان آدرس HTTPS بگذارید. سپس Actions → Android build → Run workflow را اجرا کنید.

دو Secret خصوصی `ANDROID_KEYSTORE_BASE64` و `ANDROID_SIGNING_PASSWORD` همچنان برای انتشار APK هم‌امضا لازم‌اند. نسخهٔ ۰.۳.۰ قبلاً منتشر نشده است؛ انتشار آن پس از آزمون‌ها و تطابق امضا انجام می‌شود. برای تغییر بعدی APK پس از انتشار، شمارهٔ نسخه باید افزایش پیدا کند؛ Release موجود بازنویسی نمی‌شود.

## پشتیبان‌گیری و محدودیت‌ها

دیسک `/data` و کلید رمزگذاری را در تمام دیپلوی‌ها حفظ کنید. بدون دیسک دائمی، تعویض کانتینر داده‌ها را از بین می‌برد. صرف وجود دستور `VOLUME` یا پوشهٔ `/data` در ایمیج جایگزین اتصال دیسک در پنل نیست. فایل دیتابیس `delneveshte.sqlite` و فایل‌های جانبی WAL روی همین دیسک هستند.

از snapshot دیسک یا API استاندارد backup خود SQLite در زمان اجرای اپ استفاده کنید؛ کپی‌کردن تنها فایل اصلی هنگام بازبودن اتصال ممکن است آخرین تراکنش‌ها را نداشته باشد. کپی فایل اصلی پس از توقف کامل اپ نیز ممکن است. بستهٔ خصوصی و بکاپ دیسک را جدا نگه دارید.

آزمون خودکار Docker در GitHub، کانتینر اول را حذف و کانتینر دوم را با همان Volume اجرا می‌کند؛ بانک پیام‌ها، ویرایش مدیر، نصب و گزارش ارسال باید حفظ شوند. این آزمون، راه‌اندازی واقعی در حساب هم‌روش شما نیست.

## اجرای محلی

فایل `.env.example` را به `.env` کپی و مقادیر خصوصی را وارد کنید. برای استفادهٔ کامل از پنل با کوکی امن، `PUBLIC_URL` را به آدرس HTTPS پراکسی محلی معتبر خود تنظیم کنید. سپس:

```sh
docker compose up --build -d
docker compose logs --tail=50 server
```

پورت `8080` فقط روی localhost منتشر می‌شود. `docker compose down` داده‌ها را نگه می‌دارد؛ `docker compose down -v` Volume را حذف می‌کند و برای آپدیت مناسب نیست. فایل `.env` و کلیدها هرگز نباید commit شوند.
